## 2. The three surfaces, per namespace

Every Wave 1 builder owns all three surfaces for its namespace in one pass:
`discovery.embeddingText` (dense retrieval), `description` + params (injected
context and lexical scoring), and navigation metadata (routing).

already carry `embeddingText`**, and `pickSourceText`
(`protocols/embeddings/reembed.ts:187`) prefers it over `canonicalSummary` and
over `description`. So the dense vectors currently see the description of **zero**
tools. A description-only rewrite would have left ToolSearch routing on the old
language for the entire fleet - the exact failure this batch exists to fix.

### What the distribution says, and where it misleads

**Description bytes do not track debt.** Morpho holds 42% of all description
bytes (63 KB, averaging 3.3 KB per tool) with **zero** allowlist entries, while
solana holds 11% and carries 129. The two measure different things: the
allowlist records violations of the mechanical rules, and morpho's descriptions
are long precisely because they were written after those rules existed. A
namespace builder must therefore not read "0 entries" as "nothing to do" -
morpho is the largest single body of prose the model reads, it is 21 KB of the
system prompt on top of that (see `prompt-budget-baseline.md`), and D8 length
discipline is where its review effort goes.

**The inverse also holds.** Khalani averages 320 bytes per description and holds
16 `tool-description` entries; its problem is descriptions too thin to route on,
not too long.

**The `tool-description` debt concentrates in three namespaces**: solana (49),
pendle (41) and khalani (16) are 106 of the 141 namespace-keyed entries.
Morpho, pools, uniswap and relay have none.

### Stale section comments, corrected in place

Six of the nine section headers in `_manifest-lint/allowlist.ts` and one of the
four in `internal-description-allowlist.ts` claimed counts that no longer
matched their own rows - the tables summed to a claimed 802 + 37 against an
actual 616 + 33, drifting by 186 entries as earlier waves deleted rows without
touching the headers. Corrected as comment-only edits; **no row was added,
removed or rewritten**, and the measured totals are unchanged by the correction.

These numbers are load-bearing, not decoration: each table's own doc comment
says "the length of this table is the fleet's convention debt, and it is only
allowed to shrink". A header overstating its section by 120 lets a wave delete
nothing and still look like progress.

## 5. How Wave 1 uses this

- A builder **reviews** every surface it owns and **edits** only descriptions
  failing D8, truthfulness, or the style contract. Reviewing is not editing.
- Acceptance per namespace is the row above: tool count unchanged, and each
  allowlist figure either unchanged or lower with the deleted entries named.
- An entry may be deleted only by fixing the violation. Adding an entry is not
  an available move, and the suite fails on a stale entry, so a fixed violation
  cannot be left recorded either.
- Changing `embeddingText` obliges a re-embed for that namespace plus the
  generation-health and orphan pass. Changing only `description` does not.
